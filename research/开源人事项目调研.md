## 二、frappe/hrms：模块划分与"配置即功能"

**顶层结构**（`hrms/` 目录下按业务域切分，而不是按技术层切分）：

```
hrms/
├── hr/                     # 员工档案、考勤、异动、绩效、员工自助
├── payroll/                 # 薪酬
├── recruitment/             # 招聘（Job Opening / Applicant / Interview / Offer）
├── leaves/                  # 假勤工作区（只有 workspace 配置，实体在 hr/doctype）
├── shift_and_attendance/    # 排班与打卡
├── performance/             # 绩效
├── expenses/                # 费用报销
├── tax_and_benefits/        # 税务与福利
├── tenure/                  # 司龄
├── hr_setup/                # 初始化配置（引导页）
├── controllers/ mixins/ overrides/   # 横切复用
└── patches/                 # 数据迁移脚本
```

**关键设计 1：DocType = 元数据驱动的实体。** `hr/doctype/` 下有 100+ 个目录，每个是一张"单据类型"
（`leave_application`、`leave_allocation`、`leave_ledger_entry`、`employee_transfer`、
`employee_separation`、`department_approver`…）。字段、状态、权限、视图都由配置描述，
代码只写业务钩子。好处：新增一类审批不用改框架。

**关键设计 2：审批流与业务代码解耦。** Frappe 框架提供 `Workflow` 配置
（状态 / 转换 / 允许角色 / 条件），业务单据只声明"我挂哪个 Workflow"。
请假单因此有**两套状态并存**：
- `docstatus`：0 草稿 / 1 已提交 / 2 已取消（系统级单据生命周期）
- `status`：Open / Approved / Rejected / Cancelled（业务状态）

**关键设计 3：校验集中且前置。** `leave_application.py`（1676 行）里是一串
`validate_*` 方法，全部挂在 `validate()` 上：

```
validate_dates → validate_dates_across_allocation → validate_back_dated_application
→ validate_salary_processed_days → validate_block_days → validate_balance_leaves
→ validate_leave_overlap → validate_max_days → validate_attendance
→ validate_leave_approver → validate_for_self_approval
```

这条链几乎就是"请假业务的规则清单"，直接可以抄成需求文档。

**关键设计 4：额度用账本而不是余额字段。** 同时存在
`Leave Allocation`（发放）与 `Leave Ledger Entry`（流水）两个 DocType，
余额由两者汇总得出，任何一次扣减都能追溯到具体单据。

## 三、horilla：请假模块的工程组织

`leave/` 作为一个独立 Django app，内部按"职责"而不是"技术"分文件：

```
leave/
├── models.py      # LeaveType / LeaveRequest / AvailableLeave / LeaveAllocationRequest
├── views.py  urls.py  forms.py  filters.py  sidebar.py  dashboard.py
├── cbv/           # 类视图（按页面分组）
├── services.py   # 可复用的业务方法
├── methods.py    # 模型相关的行为
├── signals.py    # 数据变更后的联动（通知、额度刷新）
├── scheduler.py 定时任务    decorators.py 权限装饰器
└── tests/
```

**状态设计**（`leave/models.py`）：

```python
LEAVE_STATUS = (
    ("requested", _("Requested")),
    ("approved",  _("Approved")),
    ("rejected",  _("Rejected")),
    ("cancelled", _("Cancelled")),
)
```

与 frappe 不同，horilla 是**单状态字段**，但把"额度申请"单独拆成
`LeaveAllocationRequest`（requested / approved / rejected）——
即"发额度"本身也是一条审批流。这个拆分很符合真实 HR：额度发放是要审的。

**值得学的两点**：
1. `services.py` / `methods.py` 把业务逻辑从 view 里剥出来，view 只做参数与渲染；
2. `signals.py` 处理"数据变了之后要联动什么"（通知、余额刷新），避免逻辑散落。

## 四、orangehrm：分层与 API-first

```
src/
├── client/     # Vue 前端（独立工程，有自己的 package.json）
├── lib/        # framework / orm / config
├── plugins/    # 模块以插件形式挂载
└── test/
web/  installer/  build/  devTools/
```

- 前后端彻底分离，前端只通过 REST API 拿数据，页面改版不影响后端；
- `lib/framework` + `lib/orm` 是自研的基础设施层，业务模块（`plugins/`）依赖它；
- 老牌商业开源，考虑的是"可二次开发 + 可升级"，所以强制分层。

## 五、共性与可借鉴清单

| # | 借鉴点 | 来源 | 本项目怎么落地 |
| --- | --- | --- | --- |
| 1 | **按业务域垂直切模块**，而不是按 controller/service 横切 | frappe/hrms、horilla | `hrflow/services/` 下按 employee / leave / report / smart_review 分文件；数据库表也按域分组 |
| 2 | **审批流配置化**（状态 + 转换 + 允许角色） | frappe Workflow | `domain/workflow.py` 实现通用 `StateMachine`，请假只是它的一个实例 |
| 3 | **审批链按"角色"路由**，不写死具体人 | frappe Department Approver | `route_approval_chain(天数, 假别)`：≤2 天主管；3–5 天主管+HR；>5 天加总监 |
| 4 | **额度用账本** | frappe Leave Ledger Entry | `leave_allocations` + `leave_ledger`，余额 = 发放 − 消耗流水 |
| 5 | **校验集中前置** | frappe `validate_*` 链 | `leave_service._validate_submit()` 一个函数里串起 8 条规则 |
| 6 | **业务状态与单据生命周期分离** | frappe docstatus/status | 本项目简化为单一 `status`，但把"终态不可再流转"写进状态机 |
| 7 | **档案变动留事件表** | frappe Employee Property History | `employee_events` 记录入转调离，from/to + 生效日期 |
| 8 | **业务逻辑从接口层剥出** | horilla services.py | API 只解析参数、捕获异常，全部委托 service |
| 9 | **额度发放本身也是审批对象** | horilla LeaveAllocationRequest | 本项目简化：`leave_allocation.source` 区分年度发放/手工补/结转，预留审批位 |
| 10 | **业务规则配置化**（假别表存额度、上限、提前天数、是否要证明） | frappe Leave Type | `leave_types` 表 + `config.HOLIDAYS`，代码里不写死"年假 10 天" |
| 11 | **前后端分离 + REST** | orangehrm | `api/server.py` 提供 REST，`web/` 是纯静态页面 |
| 12 | **可观测的流程指标** | 各家都有 dashboard | `report_service` 输出平均审批时长、部门/月度统计，作为"流程是否变顺"的度量 |

## 六、明确不照搬的部分（mini 版的边界）

成熟项目的复杂度来自"要适配成百上千家企业"，直接照抄会淹没重点：

| 不做的 | 原因 |
| --- | --- |
| 元数据驱动 / 低代码表单引擎 | 需要先造一套框架，1 天内做不完，且对 demo 没有增量价值 |
| 多租户、国际化、细粒度 RBAC 权限矩阵 | 属于平台能力，不是"人事流程"本身 |
| 薪酬计算、税务、社保 | 强地区政策依赖，做浅了不如不做 |
| 消息队列、异步任务、微服务拆分 | 单机 SQLite 场景下的过度设计 |
| 前端工程化（Vue/React + 构建链） | 目标是"打开就能跑"，原生 JS 足够表达 |

一句话：**照搬它们的"切分方式与状态机思想"，不照搬它们的体量。**
